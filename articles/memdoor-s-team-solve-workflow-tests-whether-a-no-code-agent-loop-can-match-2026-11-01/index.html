Memdoor's team-solve workflow tests whether a no-code agent loop can match a research harness

THE CONTEXT MATTERS

Main report

A repository example published under the Memdoor project on GitHub, in a directory called team-solve, presents a workflow that reproduces a research method using eight YAML files and no code, with no model named in the configuration. The workflow is described as an implementation of the method attributed to GVS5H (Lee, 2026), and its authors frame the result narrowly: the claim is parity with the original harness, not an improvement on it.[S17]

The setup is deliberately plain. A script runs the samples and decides success; the workflow itself does not. The program under test is solution.py, read from standard input and compared against the samples with diff, requiring Python 3 and bash. Every agent prompt in the workflow carries the same instruction — "fresh context, read the files, do not rely on chat" — a constraint that, according to the repository, the underlying paper credits for the method's gain.[S17]

The comparison is laid out in three columns. The authors' two columns are the regraded result files in their repository, corresponding to the numbers in their paper. The Memdoor column is stored at bench/results/parity-5pass/ and contains all 50 runs, each with every request and reply, the program produced, the grader's output and the cost. That level of logging is the point of the exercise as much as the score is: it makes each run auditable rather than leaving a headline number to be taken on trust.[S17]

The headline numbers themselves are close. The repository states plainly that on a sample this small, 9.8 and 9.6 are the same number. That is an unusually candid framing for a benchmark comparison, and it sets the boundaries of what the example can support. A 50-run sample with a gap of two-tenths of a point does not establish a performance difference in either direction; it establishes that the workflow did not visibly collapse relative to the reference harness.[S17]

One column is not like the others. Fable 5's results are one call per problem, taken from the authors' files, and were not run in this harness. That means the Fable 5 figures are a reference point carried over from the original work rather than a like-for-like measurement under the Memdoor setup. Any reader comparing across all three columns should treat that column as context, not as a controlled result.[S17]

The evaluation loop has a structural limitation that the repository acknowledges. The loop sees only the public samples; the score is computed on hidden tests. That is the standard arrangement for this kind of contest-derived benchmark, but it means the agent's feedback signal and the reported score come from different pools of problems. The workflow cannot tune against the hidden set, which is the intent, but it also means the public-sample performance is not a direct proxy for the reported figure.[S17]

There is a further caveat about the problems themselves. The contests date from spring 2025, and the repository notes that the model may have seen them in training. Contamination of this kind is difficult to rule out and harder to quantify, and it applies to any comparison involving a model trained after the contests were published. The repository does not claim to have resolved it.[S17]

Two operational details suggest the loop is not fully robust. The repository reports that twice elsewhere a correct program was overwritten and then recovered. It also states that both gaps are the authors' loop, kept as is — a decision to preserve the original method's behavior rather than patch it for the reproduction. That choice favors fidelity over reliability, and it means the workflow inherits whatever failure modes the reference implementation has.[S17]

The significance of the example lies less in its score than in its packaging. A research method described in a paper has been reduced to a set of declarative configuration files that can be inspected, diffed and rerun. The absence of a named model in the configuration is notable: the workflow is model-agnostic in its structure, and the model used for a given run is a parameter rather than a baked-in assumption. For teams evaluating agent workflows, that separation between orchestration and model choice is the reusable part.[S17]

The ledger discipline — every request, every reply, every program, every grader output, every cost figure retained per run — is what makes the parity claim checkable at all. Without it, a claim of 9.8 against 9.6 would be an assertion. With it, a reader can inspect the runs, see where the loop overwrote a correct program, and judge whether the comparison holds.[S17]

What the example does not provide is evidence of generalization. Fifty runs on contests from spring 2025, with possible training contamination and a public-sample feedback loop, cannot establish how the workflow performs on unseen problems of a different character. The repository's own framing — parity, not gain — is the correct reading of the evidence it presents.[S17]

For now, the artifact is best understood as a reproducibility tool: a way to run a published method, log it thoroughly, and compare against the original numbers without claiming to have beaten them. Whether the no-code packaging holds up when the model, the problem set or the scale changes is a question the current 50 runs are not designed to answer.[S17]

Why it matters

The example matters to teams building agent workflows because it separates orchestration from model choice and logs every run, which changes how a benchmark claim can be audited. It also matters to anyone citing the GVS5H method: the reproduction claims parity, not improvement, and the sample is small enough that the headline gap is not meaningful. The incentive it creates is toward reproducible, per-run logging rather than headline scores.

What happens next

Expect the repository to be read mainly as a template rather than a result. The open questions are whether the workflow is rerun at larger scale, whether the model used is disclosed, and whether the two overwrite incidents are patched or left as inherited behavior. None of these is settled by the current material.

What to watch

  • Any update to bench/results/parity-5pass/ adding runs beyond the current 50
  • Disclosure of which model was used in the Memdoor runs
  • A patch or documented fix for the two program-overwrite incidents
  • A rerun on contests after spring 2025 to address training contamination
  • Publication of the underlying GVS5H paper's result files for independent comparison
