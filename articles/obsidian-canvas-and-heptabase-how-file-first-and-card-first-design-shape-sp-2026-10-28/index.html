Obsidian Canvas and Heptabase: How File-First and Card-First Design Shape Spatial Notes

A comparison of the two tools' data models finds that Obsidian stores visual arrangements in standalone .canvas files, while Heptabase treats whiteboards as views over a central card library.

THE CONTEXT MATTERS

Main report

Obsidian Canvas and Heptabase both let users arrange notes on a two-dimensional whiteboard, but the two tools store those arrangements in opposite ways, according to a comparison published by fluxlinks.com on October 28, 2026. The article argues that the difference matters more than any feature checklist: Obsidian Canvas keeps visual layouts inside individual .canvas files written in the open JSON Canvas format, while Heptabase treats whiteboards as non-owning visual views over a central card library.[S8]

The distinction begins with what each tool treats as its basic unit. Obsidian is built on a local-first philosophy in which a knowledge base is a folder of plain-text Markdown files, the article states. Obsidian chose the file as its atomic unit, a decision the article credits for making a vault portable and durable. It is also why, in the article's account, a canvas can only be another file, with nowhere to store a connection except inside itself. When a user creates an Obsidian Canvas, the result is a standalone .canvas file stored on disk as JSON.[S8]

That storage model has visible consequences for notes created directly on a canvas. If a user types ten quick thought cards directly onto an Obsidian Canvas, those cards exist only inside that .canvas file, according to the article. They do not appear as independent notes in the vault unless the user manually converts them into separate Markdown files one at a time. External notes placed on a canvas are embedded views: the canvas references the file's path from the outside. When the same note is opened in Obsidian's regular editor, it does not display which canvases currently contain it, and it does not know which neighboring cards sit next to it on any canvas.[S8]

Heptabase separates what a note is from where a note is viewed, the article states. Its atomic unit is the card rather than the file. Whiteboard lines provide what the article calls a dedicated spatial linking layer that cards track wherever they are opened, while inline @mentions in card text handle linear cross-references. The practical difference the article highlights is that a line drawn on an Obsidian Canvas creates no link between notes in the vault, whereas a line drawn on a Heptabase whiteboard creates a connection both cards remember. The article also says a card in Heptabase can show every whiteboard that currently contains it.[S8]

The comparison extends to portability. Obsidian's connections are described as portable across external tools but unindexed in the vault's graph; Heptabase's connections are described as indexed across cards but locked into its proprietary ecosystem. The article says the same .md note file can be embedded across multiple .canvas files, and any text edits made to that note stay in sync. Adopting Heptabase, by contrast, requires committing to a specialized, proprietary ecosystem rather than relying on standard plain-text files, according to the article.[S8]

The article also raises limits that apply to spatial tools generally, not only to one product. It says 2D arrows lack explicit logical semantics: an arrow between Card A and Card B indicates a connection but not logic, and does not formally specify whether an idea supports a claim, refutes an assumption, or serves as a prerequisite condition. It also points to translation friction from 2D space to linear prose, noting that whiteboards arrange thoughts across spatial coordinates while essays, reports and memos are read sequentially. Bridging messy exploration and rigorous writing, in the article's view, requires modeling the logical dependencies of ideas—claims, evidence and counterarguments—rather than 2D coordinates.[S8]

The article's central recommendation is that users deciding where to build a long-term knowledge workflow should look at how each tool models files, cards and context rather than at interface features. It frames the choice as one between a file-centric architecture that keeps data in open, portable files and a card-centric architecture that indexes connections across a proprietary system. The piece also poses, as a question, whether Obsidian Canvas is fully offline and local-first compared with Heptabase, without the supplied excerpt resolving that point.[S8]

The comparison does not include pricing, performance benchmarks, user counts or independent testing of either product. Its claims rest on how the two systems are described to store and link data. For readers weighing the tools, the reported trade-off is concrete: Obsidian's approach keeps canvases as files that other tools can read, at the cost of connections that the vault's graph does not index and notes that live only inside a canvas unless converted. Heptabase's approach keeps connections visible from the cards themselves, at the cost of depending on a proprietary ecosystem rather than plain-text files.[S8]

Why it matters

The choice affects anyone building a long-term notes or research system. A file-centric design keeps data readable by other tools and durable if a product changes, but connections drawn on a canvas stay inside that canvas file and are not indexed in the vault's graph. A card-centric design makes those connections visible from every card, which helps retrieval, but ties the workflow to a proprietary system. The trade-off shapes switching costs, how easily notes can be reused, and how much of a user's thinking remains legible outside the app.

What happens next

Expect continued debate over open formats versus integrated linking as note tools compete on how they model connections. Obsidian's JSON Canvas format gives other tools a path to read canvas files, while Heptabase's card model may appeal to users who prioritize cross-whiteboard links. Neither approach resolves the article's broader point that 2D arrows do not encode logical relationships, so users may still need separate methods to move from exploration to structured writing.

What to watch

  • Adoption of the JSON Canvas format by third-party tools that can read or write .canvas files
  • Obsidian releases that change how canvas-embedded notes or connections appear in the vault graph
  • Heptabase changes to card export, data portability or whiteboard linking features
  • Public documentation or user reports on migrating canvases or cards between the two tools
  • Pricing or plan changes that affect the cost of committing to either ecosystem
